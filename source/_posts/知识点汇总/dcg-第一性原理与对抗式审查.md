# 用第一性原理+对抗式审查拆解 dcg（Destructive Command Guard）

## 一句话概括

**对一个真实的安全工具，先用第一性原理拆到最底层，再用对抗式审查找出它的盲区——看看两个思维模型在实践中能挖出什么。**

---

## 背景：dcg 是什么？

[dcg（Destructive Command Guard）](https://github.com/Dicklesworthstone/destructive_command_guard) 是一个高性能的安全防护工具，专门给 AI 编程助手用的。

**问题**：AI 编程助手（Claude Code、Codex、Gemini CLI、Copilot CLI、Cursor 等）偶尔会执行毁灭性的 shell 命令——`git reset --hard` 丢弃未提交的修改、`rm -rf ./src` 删除源代码、甚至写内联 Python 脚本 `os.remove()` 删除文件。几秒钟就能毁掉几小时没提交的工作。

**方案**：dcg 作为一个 Hook，在 Agent 执行任何 shell 命令之前拦截它，匹配预定义的"危险命令模式"，匹配上了就阻止执行并提示安全替代方案。

它用 Rust 实现，SIMD 加速达到亚毫秒级延迟，内置 50+ 安全包（核心文件系统、git、数据库、K8s、Docker、云平台等），支持几乎所有主流的 AI 编程工具。

---

## Part 1：第一性原理分析

按照这个思维模型的框架，把 dcg 拆到不可再分的基本事实。

### 第一步：识别并拆解所有假设

| 常规认知 | 追问 |
|---|---|
| "Agent 知道自己在干什么" | 它是概率模型，可能产生完全错误的命令 |
| "人能及时发现问题" | 快速迭代中不可能盯着每条命令 |
| "危险命令很明显" | `rm -rf $DIR` 变量为空时变成 `rm -rf /`，极其隐蔽 |
| "操作系统权限就够了" | Agent 通常在用户权限下运行，有完整破坏力 |
| "禁止危险操作就安全了" | 创造性绕过方式数不胜数 |

### 第二步：找到底层事实

我们到底在解决什么问题？

> 一个随机性系统（LLM）被允许向一个确定性系统（Shell）发送指令，而 Shell 会忠实地执行任何它收到的命令——包括那些不可逆的破坏操作。

**不可再分的基本元素：**

1. **命令生成器（Agent）** — 概率性的，不完美，可能犯错
2. **命令（字符串）** — 可以被解析、分析、分类
3. **执行环境（Shell + OS）** — 无条件服从，除非被拦截
4. **受保护资产（数据/代码）** — 我们要保护的东西
5. **时间窗口** — 从命令生成到执行之间的微小间隔，这是唯一可以干预的时刻

### 第三步：从事实重新推导

从这些底层事实出发，一个理想的命令守卫**必须**满足：

1. **比人快** — 亚毫秒级拦截 ✅ dcg 做到了（SIMD 加速）
2. **理解语义而非仅语法** — ⚠️ 正则匹配只能覆盖已知模式，无法理解抽象的"破坏意图"
3. **默认拒绝危险操作** — ✅ 核心包（core.filesystem、core.git）默认开启且不可禁用
4. **可绕过但可审计** — ✅ 有 `DCG_BYPASS`、`allow-once`、白名单等多种绕过方式，均有日志记录
5. **深度理解多步攻击** — ⚠️ 单命令级别保护，多步组合攻击是盲区

这个推导过程告诉我们：dcg 的设计方向是对的——拦截点摆在命令执行前是唯一有效的干预窗口，亚毫秒级延迟是不影响工作流的硬约束——但它的底层逻辑本质上是 **"签名匹配"**，这意味着它天生有认知上限。

## Part 2：对抗式审查

现在站到对面去——假设我是一个攻击者（或者是一个被恶意提示词污染的 Agent），我要绕过 dcg。

### 第一层：事实检查

**声明**：dcg 支持所有主流 AI 编程工具
**事实**：没错，它确实集成了 Claude Code、Codex、Gemini CLI、Copilot CLI、Cursor、Hermes Agent、Grok 等。✅

**声明**：亚毫秒级延迟
**事实**：Rust + SIMD 加速，确实能做到亚毫秒级别。✅

**声明**：50+ 安全包，覆盖数据库、K8s、Docker、云平台
**事实**：这些包默认是不开启的——用户需要手动配置 `[packs] enabled`。`dcg init` 生成的 starter config 会开启 postgresql 和 docker 作为示例，但无 config 文件时只启用 `core.filesystem`、`core.git`、`system.disk`。❌ **这里的表述有误导风险——用户容易以为是开箱即全保护的。**

### 第二层：逻辑检查

dcg 的核心逻辑链条：**解析命令 → 匹配模式库 → 决定阻止/放行**

这个链条本身没问题。但有一个逻辑漏洞：

> 这个链条假设"危险 = 可以被正则匹配到的模式"。

从第一性原理我们知道：破坏意图可以通过无数种方式表达，而正则表达式只能覆盖已知的表达方式。

### 第三层：完整性检查

以下是 dcg 文档中没有强调，但真实存在的**结构性盲区**：

#### 🟡 盲区一：多步攻击

dcg 检查的是**单条命令**，但破坏可以分几步完成，每步单独看都不危险：

```bash
# 第一步：写脚本（看起来无害）
echo 'rm -rf / --no-preserve-root' > /tmp/x.sh

# 第二步：执行脚本（"执行一个文件"本身不危险）
bash /tmp/x.sh
```

更隐晦的版本：
```bash
# 写 Python 脚本
cat > /tmp/cleanup.py << 'EOF'
import shutil
shutil.rmtree('/home/user/project/src')
EOF

# 执行 Python
python3 /tmp/cleanup.py
```

#### 🟡 盲区二：跨语言绕过

将任意高级语言当作 shell 使用，每一条都不触发 dcg 的匹配规则：
```bash
python3 -c "import os; os.system('rm -rf /')"
ruby -e "system('rm -rf /')"
perl -e "system('rm -rf /')"
node -e "require('child_process').execSync('rm -rf /')"
```

dcg 声称能扫描内联脚本，但深度取决于实现——多层嵌套、字符串拼接、变量插值都可能绕过。

#### 🔴 盲区三：编译型攻击

绕过 Shell hook 最彻底的方式——编译执行完全不走 Shell 的匹配路径：
```bash
# 写 C 代码（纯文本，无害）
echo '#include <stdio.h>' > /tmp/destroy.c
echo 'int main() { system("rm -rf /"); }' >> /tmp/destroy.c

# 编译（也不是危险命令）
gcc /tmp/destroy.c -o /tmp/destroy

# 执行（看起来只是一个普通程序）
/tmp/destroy    ← dcg 不拦截！
```

#### 🟡 盲区四：容器逃逸

如果 `containers.docker` 包没开（默认不开），这个完全放行：
```bash
docker run --rm -v /:/mnt ubuntu rm -rf /mnt
```

#### 🟡 盲区五：远程/编排执行

本地命令看起来完全无害，破坏发生在远端：
```bash
ssh other-server 'rm -rf /'
ansible all -m shell -a 'rm -rf /'
```

#### 🔴 盲区六：绕过机制自身

最致命的不是绕过，是**让 Agent 自己解除防护**：
```bash
# Agent 写配置文件解除保护
echo 'disabled_packs = ["core.git", "core.filesystem"]' >> ~/.config/dcg/config.toml

# 或积累白名单，慢慢蚕食防护边界
dcg allowlist add core.filesystem:recursive_rm -r "project cleanup"
```

#### 🟡 盲区七：环境变量绕过

DCG_BYPASS=1 作为单命令逃生口是合理的设计，但这也意味着——如果 Agent 能设置环境变量（它当然能），整个保护就是 opt-out 的：
```bash
DCG_BYPASS=1 rm -rf /
```

### 第四层：动机检查

dcg 的开发者 Jeffrey Emanuel 最初写这个工具的动机很清晰——他自己的 AI Agent 毁了他的工作，他想要一个解决方案。这个动机是诚实的，**不存在利益冲突**。

但有一个隐含的动机问题：**dcg 是一个签名系统**，签名系统的维护者天然有动机让签名库变得更大、更全——这本身是好事，但容易造成"签名多了就安全了"的幻觉。**更危险的不是不知道的模式，而是知道但没关联起来的模式。**

### 第五层：修复建议

| 层级 | 问题 | 严重度 | 建议修复 |
|---|---|---|---|
| 事实 | 50+ 安全包默认不开，表述易误导 | 🟡 | 文档明确标注"默认仅开启 core.* + system.disk" |
| 逻辑 | 签名匹配无法理解语义，只能匹配已知模式 | 🔴 | 这是结构性限制，文档应承认边界，不能暗示全覆盖 |
| 完整 | 多步攻击完全盲区 | 🔴 | 引入命令序列分析：记录上下文，检测"写入→执行"的时序模式 |
| 完整 | 编译型攻击完全盲区 | 🔴 | 可在编译阶段插入 hook，但比较复杂；更务实的方案是用 seccomp/LSM 做 syscall 级防护 |
| 完整 | 远程/编排执行盲区 | 🟡 | SSH 命令检测可以加强，但远端的保护需要 Agent 端也装 dcg |
| 完整 | Agent 可自行解除防护 | 🔴 | 核心包禁止配置文件关闭、环境变量绕过需要用户手动确认 |
| 完整 | 跨语言内联脚本扫描深度有限 | 🟡 | 更深入的内联代码解析器，检测字符串拼接、编码后的命令 |

## 关键洞见

### 1️⃣ dcg 的本质

dcg 的底层逻辑是一个 **签名白名单系统**——它知道"看起来危险"的命令模式并匹配拦截。它擅长的是**防御已知危险模式的直接执行**，对`rm -rf /`、`git reset --hard`、`DROP TABLE`这类经典破坏有极好的防护效果。

但真正的危险不是单条命令本身，而是**用户的操作意图被歪曲**。一个足够聪明的 Agent 可以通过无数条"看起来安全的单步操作"组合出任意破坏力。逐个检查每条命令是否安全，类似于逐个检查每个字母是否包含敏感词——你总会漏掉组合起来的含义。

### 2️⃣ 更好的比喻

这不是"安检机"——安检机能检查所有行李，因为行李是一次性通过的。

这是更像**一个能检查每个字的拼写检查器，但无法检查整个句子的含义**。单字没错不等于句子没问题。

### 3️⃣ 真正有效的防御

dcg 是安全拼图中的**一块**，不是全部。从第一性原理推导，结合对抗式审查的发现，真正有效的多层防御应该是：

```
第一层（基础）：dcg 拦截已知危险命令
第二层（增强）：最小权限容器（Docker/VM），即使命令放行了，破坏范围也受限
第三层（审计）：预览"汇总变更"（类似 git diff 的 command diff），执行前让人确认
第四层（容灾）：自动快照/备份，即使出了问题也能恢复
```

## 结论

dcg 是一个**设计优秀、实现精良的签名式命令守卫**。它在自己的范围内（已知危险模式的单命令拦截）做得非常好。但它不是一个魔法盾牌——对它能力边界的不清晰认知，比不用它更危险。

最好的使用方式：
1. **装上它**——它能挡住 90% 的常见意外破坏
2. **配合沙箱**——让 Agent 跑在受限环境里
3. **保持备份**——任何安全工具的最后一层都是"还能恢复"
4. **理解它的边界**——知道它防不住什么，比知道它防得住什么更重要

**对工具谦卑，对威胁认真。这就是全部。**
