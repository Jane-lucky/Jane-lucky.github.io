reverse-skill 技能解析：为什么逆向可以是工程，而不是玄学

reverse-skill 技能解析：为什么逆向可以是工程，而不是玄学

一句话概括

reverse-skill 把”逆向一个加密/混淆的网页 JS”这件事，从凭感觉试错，变成一条有门禁、有状态、可交接的工程流水线——它解决的核心问题不是”看不懂代码”，而是”不知道自己卡在哪一步、缺什么证据、下一步该干什么”。

它是什么

reverse-skill（715494637/reverse-skill）是一个面向 Web JS 逆向分析的 AI Agent 技能包。核心入口是 jsr-reverse，一套按既定流程运行的逆向作战手册。

它交付的资源：

  • 一套 7 阶段强制流程：任务归一化 → 证据采集 → 定位 → 恢复 → 运行时 → 验证 → 交付
  • 复杂度分级（L1~L4）：先判断活有多大，再校准投入
  • 阶段门禁 + 状态契约：每个阶段有进入条件、必交付物、退出条件、失败输出
  • 19 篇专题 reference：AST 反混淆、JSVMP 恢复、运行时诊断、请求链记录、瑞数恢复锚点等，按需只读相关篇目
  • 交接工件：reverse-records/请求链路.md，专为”会话会断、人会忘”设计
  • 配套工具：js-reverse-mcp（驱动真实浏览器插桩取证的 MCP 服务）

第一性原理：逆向真正难的是什么

很多人以为逆向的难点是”代码看不懂”。但你盯着一坨混淆 JS 看三小时，往往不是读不懂，而是不知道现在卡在哪一步：

  • 目标是加密参数，可它到底在哪被写入的？没人证明，只是猜。
  • 本地跑出来的结果和浏览器不一样，是环境差异、时序问题，还是指纹风控分支？
  • 做了一半，睡一觉/换了会话，进度全丢，又要从头翻代码。

reverse-skill 的第一性原理拆法很直接：逆向的本质是一个”证据链闭合”的过程，而不是一次”看懂代码”的灵光一闪。 既然它是一段多阶段、长耗时的推理，那它就该被当成工程来管——有阶段、有门禁、有状态、有留痕。

这套逻辑，和”对抗式审查”其实是同一个思想：不轻信”我觉得是这样”，只接受”有证据证明是这样”。

核心：7 阶段工作流脊柱

每个阶段都强制回答”凭什么”：

阶段 要回答的问题 必交付物
任务归一化 目标是什么、触发方式、成功标准 任务卡
证据采集 有没有可信的真实样本 样本包
定位 参数到底在哪被写入（writer/sink） 请求链路.md
恢复 混淆壳剥到什么程度能读懂逻辑 恢复记录
运行时 浏览器和本地为什么结果不一样 运行态清单
验证 本地算法 == 浏览器真实行为？ 验证记录
交付 交付什么、禁止交付什么、残余风险 交付清单

关键规则：做完一半不许硬往下冲，做错了要回退到差异所在的阶段。 这一条直接掐死了逆向里最常见的失败模式——“我猜了个大概就往下写代码，结果错得很远”。

复杂度分级：先判断这活有多大

级别 场景 要走几个阶段
L1 参数是明文拼接，无混淆、无环境依赖 定位 → 验证
L2 单层混淆 / webpack 包 + 一次加密调用 加恢复
L3 JSVMP / WASM / worker 桥 + 环境依赖 + 反调试 全流程
L4 对抗级：瑞数(RS)、多跳 cookie、动态代码、指纹风控 全流程 + 多轮迭代

分级不是用来”绕过流程”的，而是用来校准每次投入：L1 的活别杀鸡用牛刀，L4 的活别指望一次跑通。而且规则写死了一条：级别只能往上修正，不能没证据就往下调。

工程化的精髓：状态契约 + 证据门禁

这是整个技能最值钱的部分，也最值得抄作业：

五种状态，杜绝”半成品硬冲”
就绪 / 部分完成 / 阻塞 / 失败 / 不可交付

  • 缺目标、缺样本 → 只能是 阻塞，不能假装开工
  • 做过一半、证据没闭环 → 只能是 部分完成，禁止向后冒进
  • 验证不通过 → 只能是 失败，回退到差异所在的阶段

证据门禁（Evidence Gate）：只要目标请求还没从真实样本确认、上游依赖链还是在猜、多种假设没有记录来裁决——就先别选阶段，先把证据补齐。

一句话：它不信任”感觉”，只接受”证据”。 这正是对抗式审查的要义——每一条结论都要能指出它的依据，否则就是未证实。

为 LLM 会话压缩而生的交接工件

逆向任务经常跨天，LLM 会话一压缩，之前的判断全模糊了。reverse-skill 的解法很朴素：**把所有阶段结论写成 reverse-records/请求链路.md**（请求区块 + 运行时补充 + 恢复补充 + 验证补充），断在哪就从哪续。

续接时，新会话只需要一句话：

模型读完交接文档，就能归一化目标、固定样本、接着补证据继续推进。这是为”AI 会忘事”这个客观缺陷设计的制度性补偿，而不是靠模型自觉。

这也解释了为什么这个 repo 里反直觉地堆了大量 docs：它不是工具，是一套能让任何 agent（甚至任何人）接手不掉链子的流程规范。

配套工具

js-reverse-mcp：独立的 MCP 服务，让 AI 能驱动真实 Chrome 插桩调试——断点上下文求值、脚本源码导出、请求调用栈、WebSocket 分析、浏览器状态重放。反检测默认走 Patchright 协议层 stealth，对强反爬站点可切 CloakBrowser 源码层指纹模式。

对抗式审查：这套设计的可借鉴点与边界

值得借鉴的：

  • 把”长链路推理”显式拆成有门禁的阶段，是任何复杂 Agent 任务（不只逆向）都该学的结构
  • “证据驱动 + 状态契约”直接对抗 LLM 的过度自信和会话遗忘
  • 分级校准投入，避免小马拉大车或大炮打蚊子

边界与风险：

  • 高度垂直：只解决 Web JS 逆向，不适用于移动端、非 JS 场景
  • 流程本身有学习成本：小任务硬套全流程会显得笨重
  • 这是一个对抗反爬领域的技能，实际用于真实站点时要特别注意目标的使用条款与合规边界——方法论可以学，用途要守界

对我们的启示

reverse-skill 最打动我的，是它体现的思维方式：不把复杂任务寄希望于”跑一次就成功”，而是设计成”每一步都有证据、断了能续上、错了能回退”。 这和我一直在整理的「第一性原理 + 对抗式审查」是同一套内核——先拆到最底层，再用证据闭合每一条推理。

工具本身很垂直，但”用工程化驯服玄学任务”的思路，值得任何一个做 AI Agent、写复杂自动化的人抄走。
