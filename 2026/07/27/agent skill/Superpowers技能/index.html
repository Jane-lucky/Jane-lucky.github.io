Superpowers技能

Superpowers技能

一句话概括

在动手做任何事之前，先检查有没有现成的技能可以帮你做——因为”重新发明轮子”是最大的浪费。

为什么需要它？

回到一个底层事实：你面对的绝大多数问题，别人已经解决过了，而且把解法封装成了可复用的工具。

但人（和AI）的本能是什么？

  1. 直接上手——“这事儿我能搞定”，然后从零开始
  2. 先问再干——“让我先搞清楚情况”，但搞清楚的方式是瞎摸索
  3. 凭记忆干——“我记得大概怎么做”，但记忆会过时、会遗漏

这三种本能都有一个共同缺陷：没有先检查”有没有更好的方法已经存在”。

Superpowers 的本质就是一条硬规则：

在响应任何请求之前，先扫描所有可用技能。如果有技能匹配，你必须用它，而不是自己从头来。

它到底是什么？

从第一性原理拆开：

1. “Super”——超越你原生能力的东西

你裸跑能做的事是有限的。技能（Skill）是什么？是别人把最佳实践、领域知识、操作步骤打包成了一份可执行的指南。

  • 你裸跑写前端 → 可能写出模板化的页面
  • 你用 design-taste-frontend 技能 → 按照反套路的设计标准写，结果完全不同

技能 = 你的能力 × 外部沉淀的智慧（比喻，不是数学公式——但方向是对的）

这就是”Super”的含义——不是你变强了，是你站在了别人的肩膀上。

2. “Powers”——复数，不是一个，是一整个军火库

Superpowers 不是单一技能，是一个调度系统——它管理你对所有技能的发现、匹配和调用。

它的核心能力：

  • 发现：扫描可用技能列表，找到和当前任务匹配的
  • 匹配：根据任务描述，判断哪个技能最相关
  • 调度：按优先级排列，先调过程类技能（定方法），再调实现类技能（干活）
  • 强制：不是”建议你用”，是”你必须用”——这是规则，不是建议

3. 合起来

Superpowers = 一个强制性的技能调度系统，确保你在做任何事之前，先找到并使用最合适的已有技能，而不是从零开始。

核心规则

Superpowers 只有一条铁律，但它是绝对的：

如果有一个技能可能适用于你正在做的事，你必须调用它。没有例外。

这不是”建议”，不是”最佳实践”，是规则。违反这条规则的行为包括：

你可能的想法 现实
“这只是个简单问题” 简单问题也可能有技能能做得更好
“我先探索一下再说” 技能会告诉你怎么探索，先查技能
“我记得这个技能怎么用” 技能会更新，记忆会过时，读最新版
“用技能太重了” 简单的事变复杂了才知道痛，先用了再说
“我自己能搞定” 能搞定 ≠ 搞定得好，技能可能做得更好

技能优先级：过程 > 实现

当多个技能同时适用时，有明确的调度顺序：

先调过程类技能（定方法），再调实现类技能（干活）。

如果反过来——先调实现类技能直接开干——你可能做出一个技术上完美但方向完全错误的东西。

先想清楚，再动手。Superpowers 强制执行这个顺序。

但注意：在时间极度紧迫或纯探索性任务中，过程类技能可以简化或跳过——规则是活的，目标是死的。

它和”直接干”的区别

直接干 用Superpowers
第一步 开始写代码/写文档 扫描技能列表
方法来源 自己的经验和直觉 别人沉淀的最佳实践
质量天花板 受限于个人经验 受限于社区最佳实践
出错模式 重复别人已踩过的坑 跳过已知坑，犯新坑
速度 看起来快（直接上手） 实际快（少走弯路）

工作流

常见误区

❌ 误区一：Superpowers是某个具体技能

不是。Superpowers 本身不干活，它调度其他技能干活。它是质检员——在开工前先检查你有没有用对工具，而不是替你干活。

❌ 误区二：每个任务都要走完所有技能

不是。只调用相关的技能。写前端用设计技能，修bug用调试技能，不需要把所有技能都过一遍。

❌ 误区三：技能可以替代思考

不是。技能提供的是框架和方法，不是替你思考。你仍然需要理解问题、判断适用性、做出决策。技能帮你少走弯路，不帮你走路。

❌ 误区四：技能结果一定比裸跑好

不一定。技能是工具，工具用错场景比不用还糟。关键在于匹配——技能和任务的匹配度决定了结果质量。

技能生态：发现、安装、组合

Superpowers 不是孤立的，它运行在一个技能生态中：

发现

  • 内置技能：系统预装的，开箱即用（如 brainstorming、systematic-debugging）
  • 社区技能：从 ClawHub 等市场发现和安装（类似 npm 生态）
  • 自建技能：你自己写的，针对你的特定工作流

安装

技能通常以 SKILL.md + 脚本/模板的形式存在。安装后出现在 <available_skills> 列表中，Superpowers 就能发现和调度它。

组合

多个技能可以协同工作，常见模式：

  • 顺序组合：brainstorming → writing-plans → executing-plans（先想后写再干）
  • 条件组合：systematic-debugging 发现问题后，按问题类型调用对应领域技能
  • 并行组合：多个独立子任务各调各的技能（如 dispatching-parallel-agents）

关键原则：技能之间不要冲突——如果两个技能给出矛盾指引，以更具体的那为准，或停下来问用户。

Superpowers 专有技能

Superpowers 仓库（obra/superpowers）包含以下 14 个技能，全部是过程/工作流类：

技能 用途
using-superpowers 本技能——确保任何任务开始前先查技能
brainstorming 任何创造性工作前的需求探索和设计讨论
writing-plans 有规格/需求的多步骤任务，动代码前先写计划
executing-plans 按写好的实施计划，在独立会话中分步执行
systematic-debugging 遇到 bug、测试失败、异常行为时的系统化排查
test-driven-development 实现功能或修 bug 前，先写测试
verification-before-completion 声称完成前，先跑验证命令确认结果
requesting-code-review 完成任务/大功能后，发起代码审查
receiving-code-review 收到审查反馈后，先验证再实施
subagent-driven-development 用子代理并行执行计划中的独立任务
dispatching-parallel-agents 2+ 个互不依赖的任务并行分发
using-git-worktrees 需要隔离工作区时，用 git worktree 创建
finishing-a-development-branch 实现完成、测试通过后，决定如何集成
writing-skills 创建/编辑/验证技能

💡 系统中还安装了其他来源的技能（设计类、平台集成类、工具类等），Superpowers 同样可以调度它们，但它们不属于 Superpowers 仓库本身。

它的代价

  • 启动成本：每次任务前都要扫描和判断，有少量额外时间开销
  • 过度依赖：如果技能指南有错或过时，你会跟着错——而且因为”这是技能说的”而更自信地错
  • 灵活性降低：技能有固定流程，有时你的任务需要跳出流程做非常规操作
  • 技能质量参差：不是所有技能都同等好，差的技能比裸跑更糟

什么时候该用？ 当存在匹配的技能且技能质量可信时。什么时候可以跳过？ 用户明确说”不用技能”，或技能质量存疑、匹配度低的时候。

现实中的类比

  • 军事：指挥官不会让士兵自己想办法打仗——有战术手册、有作战条例、有参谋体系。Superpowers 就是 AI Agent 的参谋体系
  • 医疗：医生看病不会凭感觉开药——有临床指南、有诊疗规范。技能就是 AI 的临床指南
  • 航空：飞行员起飞前有检查清单（checklist）——不是因为他们不会飞，是因为清单防止遗漏。Superpowers 就是 AI 的起飞前检查清单

最后一句

Superpowers 的核心不是”让你变强”，而是”让你不犯已知的蠢”。

世界上最昂贵的错误，不是你不知道的，而是你以为你知道但其实不知道的——Superpowers 强制你先查再干，就是为了堵住这条。
