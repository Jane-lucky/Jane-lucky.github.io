Embedding与Ranker模型

Embedding与Ranker模型

一句话概括

Embedding 把文本变成向量，让”语义相似”可以计算；Ranker 把候选结果重新排序，让”最相关的”排到最前面。一个是检索的基石，一个是精排的利器，RAG 里两个缺一不可。

上篇：Embedding 模型

为什么需要它？

回到一个底层问题：计算机只认识数字，不认识”意思”。

你说”退款”和”退货”，人一看就知道是相关的。但计算机看到的是两串不同的字符——它怎么知道这两个词有关系？

传统方案：

方法 做法 问题
关键词匹配 “退款”包含”退”→匹配”退货” “如何退钱”就匹配不到了
同义词表 人工维护”退款≈退货≈退钱” 维护成本高、覆盖不全、无法理解句子级语义
TF-IDF/BM25 基于词频统计 字面不同但语义相同的句子，得分很低

这些方法的共同缺陷：它们只看”字面”，不看”意思”。

Embedding 的本质：把文本映射到一个数学空间，让”意思相近的文本”在空间中距离近。 这样，”语义相似”就变成了”向量距离近”——一个可以精确计算的东西。

原理：Embedding 到底做了什么？

核心思想

把任意长度的文本 → 固定维度的向量（如 768维、1024维、1536维）

语义相近 → 向量距离近；语义不同 → 向量距离远。 这就是 Embedding 的全部承诺。

怎么衡量”近”？

常用余弦相似度：

为什么用余弦而不是欧氏距离？因为向量的长度受文本长度影响，而方向代表语义。余弦相似度只看方向，不看长度——更纯粹地衡量语义。

训练原理（简化版）

Embedding 模型怎么学会”意思相近的文本向量也相近”？

核心方法：对比学习（Contrastive Learning）

经过海量文本对训练后，模型就学会了：语义关系 → 向量空间中的几何关系。

选型建议

怎么看评测排行榜？

选模型不能只看名字，要看数据。两个关键基准：

  • MTEB（Massive Text Embedding Benchmark）：英文 Embedding 的标准评测，涵盖分类、检索、聚类、重排序等任务。看”Retrieval”子项的分数最 relevant
  • C-MTEB：中文版 MTEB，智源维护。选中文模型必看

注意：排行榜分数 ≠ 你的场景效果。排行榜是通用数据集，你的领域可能不同。最佳实践：用排行榜缩小候选范围（Top-3~5），然后在你自己的数据上评测，用数据做最终决策。

Embedding 实战要点

1. 维度选择

维度越高，表达能力越强，但存储和计算成本也越高。

维度 存储成本/条 检索速度 适合场景
384 ~1.5KB 最快 对速度敏感、数据量大
768 ~3KB 快 通用场景
1024 ~4KB 中 中文RAG
1536 ~6KB 较慢 追求精度
3072 ~12KB 慢 极致精度

实际建议：1024 维是当前性价比甜点——精度够用、速度可接受。

2. 输入长度限制

Embedding 模型有最大输入长度（token 数），超长文本会被截断：

模型 最大长度 超长怎么办
OpenAI text-embedding-3 8192 tokens 截断（前面或后面丢掉）
bge-large-zh 512 tokens 需要先切分再分别嵌入
bge-m3 8192 tokens 支持长文本

关键：切分文档时，chunk 大小不能超过 Embedding 模型的最大输入长度——否则信息被截断，检索质量下降。

3. 归一化

有些模型输出已归一化（向量长度=1），有些没有。计算余弦相似度前要确认——如果已归一化，余弦相似度就等于点积，计算更快。

Embedding 优化策略

1. 领域微调

通用 Embedding 模型在你的领域可能表现差——医疗、法律、金融的术语它理解不准。

解法：用领域数据微调 Embedding 模型

效果：领域内检索准确率可提升 10~30%

2. 查询指令（Instruction Prefix）

有些模型支持给查询加指令前缀，让模型知道”你要用这个向量做什么”：

为什么有效？ 同一段文本，”用于检索”和”用于分类”的最优向量表示不同。指令前缀让模型知道当前的任务。

3. 多向量表示（ColBERT 风格）

传统方法：一段文本 → 一个向量。问题：长文本信息压缩到一个向量，丢失细节。

ColBERT：一段文本 → 每个token一个向量，相似度用 MaxSim 计算。

优势：细粒度匹配，长文本效果好。代价：存储量翻几十倍（约30~50倍），检索更复杂，工程成本高。判断：除非你的场景对精度要求极高且数据量可控，否则稠密+稀疏混合（BGE-M3风格）是更务实的选择。

4. 稠密+稀疏混合表示（BGE-M3 风格）

同时输出稠密向量（语义）和稀疏向量（关键词），检索时两者结合：

优势：语义匹配 + 关键词匹配，两全其美。这是当前性价比最高的方案。

下篇：Ranker 模型

为什么需要它？

Embedding 检索（粗检索）拿到 Top-K 结果后，存在一个问题：

向量相似度高 ≠ 真正相关

原因：

问题 举例
语义漂移 问”苹果手机价格”，检索到”苹果水果的价格”——“苹果”语义模糊
粗排不准 Embedding 是双编码器（Bi-Encoder），query和doc独立编码，无法交互
长尾偏差 训练数据中少见的组合，相似度计算不可靠
位置偏差 Top-1 不一定是最相关的，只是向量距离最近的

Ranker 的本质：对粗检索的结果做精排，用更精细的模型判断每条结果和 query 的真实相关度。

原理：Ranker 和 Embedding 的根本区别

双编码器（Bi-Encoder）= Embedding

特点：query 和 doc 独立编码，互不感知。速度快（向量可预计算），但精度有上限——因为 doc 编码时不知道 query 是什么。

交叉编码器（Cross-Encoder）= Ranker

特点：query 和 doc 一起编码，模型可以看到 query 和 doc 的每个 token 之间的交互。精度高，但速度慢——每对 (query, doc) 都要过一遍模型，不能预计算。

直觉理解

  • Bi-Encoder：像看两张照片判断是不是同一个人——各自独立看，凭记忆比对
  • Cross-Encoder：像把两张照片并排放一起看——可以逐像素对比，判断更准

精度：Cross-Encoder > Bi-Encoder
速度：Bi-Encoder >> Cross-Encoder（快几百倍）

这就是为什么 RAG 用两阶段检索：先用 Bi-Encoder 粗检索（快），再用 Cross-Encoder 精排（准）。

选型建议

Ranker 实战要点

1. 粗检索取多少条给 Ranker？

粗检索Top-K 给Ranker的数量 精排后取Top-N 建议
5 5 3 不需要Ranker，粗检索够用
20 20 5 常见配置，性价比好
50 50 5 精排更准，但延迟增加
100 100 10 大规模场景，延迟明显

经验值：粗检索 2050 条，精排后取 Top-35，是大多数场景的甜点。

2. Ranker 的输入长度限制

Cross-Encoder 要把 query + doc 拼在一起过模型，有总长度限制：

模型 最大输入
bge-reranker-v2-m3 8192 tokens
ms-marco-MiniLM 512 tokens
Jina-reranker-v2 8192 tokens

如果 doc 太长：只取 doc 的前 N 个 token（截断），或只取和 query 最相关的段落。

3. 分数归一化

不同 Ranker 输出的分数范围不同（有的01，有的-1010，有的任意范围）。如果需要跨模型对比或设阈值过滤，要先归一化。

4. 延迟优化

Cross-Encoder 慢，优化方法：

  • 批量推理：一次送多对 (query, doc) 进模型
  • GPU加速：Ranker 推理用 GPU，比 CPU 快 10~50 倍
  • 只对粗检索结果精排：不要对全库精排，只对 Top-K 精排
  • 模型蒸馏：用大 Ranker 蒸馏出小 Ranker，速度翻倍

Ranker 优化策略

1. 级联精排

粗检索结果量大时，用多级精排逐步过滤：

优势：兼顾速度和精度。轻量级快速过滤掉明显不相关的，重量级只处理少量候选。

2. LLM-based Reranker

用大语言模型（GPT-4、Qwen等）做 rerank：

优势：理解能力最强，能处理复杂语义。代价：极慢、极贵——每条结果都要调一次LLM。只适合对精度要求极高的场景。

3. List-wise Reranker

Point-wise：逐条打分 → 可能所有分数都很高，区分度差
List-wise：把所有候选放一起比较 → 区分度好

4. 领域微调 Ranker

和 Embedding 一样，通用 Ranker 在特定领域可能不准。用领域数据微调可以显著提升：

Embedding vs Ranker 全景对比

维度 Embedding（Bi-Encoder） Ranker（Cross-Encoder）
输入 单条文本 文本对 (query, doc)
输出 向量（高维） 相关度分数（标量）
编码方式 query和doc独立编码 query和doc交互编码
速度 快（向量可预计算） 慢（每对都要过模型）
精度 中（有上限） 高（交互带来精度提升）
用途 粗检索、聚类、分类 精排、重排序
可预计算 ✅ doc向量提前算好存起来 ❌ 必须和query一起算
存储 向量数据库 无需额外存储
在RAG中的角色 从全库中快速找到候选 从候选中挑出真正相关的

一句话总结它们的关系：

Embedding 是海选——从万人中快速筛出50个候选人；Ranker 是决赛——让评委面对面仔细打分，选出真正的Top-5。

常见误区

❌ 误区一：Embedding 检索够准了，不需要 Ranker

小数据量+简单问题可能够用。但数据量一大、问题一复杂，粗检索的噪音就会暴露。Ranker 是 RAG 质量的关键提升点，投入产出比极高。

❌ 误区二：Ranker 可以替代 Embedding

不行。Ranker 太慢，不能对全库逐条打分——它只能对少量候选精排。必须先粗检索缩小范围，再精排。

❌ 误区三：Embedding 模型越大越好

不一定。大模型精度高但延迟高、成本高。对很多场景，1024维的中等模型就够用了。选型要看场景，不是看参数量。

❌ 误区四：所有文本用同一个 Embedding

query 和 doc 的最优表示不同。有些模型（BGE系列）推荐 query 加指令前缀。忽略这个细节，检索质量会打折扣。

它们的代价

Embedding 的代价

  • 计算成本：建库时全量编码，数据量大时GPU时间不低
  • 存储成本：每条文档一个向量，百万级数据存储量可观
  • 更新成本：文档变了要重新编码，增量更新需要设计
  • 维度诅咒：维度太高，向量空间中欧氏距离趋同（”远近”失去意义），检索效果反而下降。不过余弦相似度受影响较小（归一化后只看方向），所以当前主流用余弦相似度可以部分缓解，但维度也不是越高越好

Ranker 的代价

  • 延迟：每对 (query, doc) 都要过一遍模型，50条候选 × 10ms/条 = 500ms 额外延迟
  • GPU需求：Cross-Encoder 推理最好用GPU，CPU太慢
  • 长度限制：query+doc 总长度有上限，超长doc要截断
  • 无法预计算：每次查询都要实时计算，不能提前算好

最后一句

Embedding 解决”能不能搜到”的问题，Ranker 解决”搜到的东西对不对”的问题。

一个 RAG 系统中，Embedding 决定召回率（相关文档能不能进候选集——这是下限，搜不到就什么都没了）；Ranker 决定排序质量（进来的候选排得对不对——这是上限，排错了好结果被埋没）。两个都调好，RAG 才能真正靠谱。
